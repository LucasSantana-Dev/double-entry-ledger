# Cost map, 2026-11-16

What it would cost to run the ledger stack (application, PostgreSQL 18, single-node Kafka) on one small cloud machine, from the footprint measured in phase 5. Nothing was deployed ([ADR 0026](../adr/0026-no-public-deployment-cost-map-instead.md)). The prices are on-demand list prices; no bill backs them.

## Footprint

Measured with `python tools/footprint/footprint.py` on Docker Desktop (WSL2, 16 CPUs): the stack without the observability container, `deploy/smoke.sh`, 10,000 transfers from 64 threads with 30% touching one account, `deploy/smoke.sh` again, then a wait until the outbox is drained and the ledger checks pass. Peak memory is the highest `docker stats` sample over the run, without page cache.

| | baseline | lean settings | lean settings + AOT cache |
|---|---|---|---|
| application peak MiB (limit) | 859 (none) | 516 (768) | 465 (768) |
| PostgreSQL peak MiB (limit) | 119 (none) | 91 (256) | 91 (256) |
| Kafka peak MiB (limit) | 482 (none) | 437 (576) | 428 (576) |
| total peak MiB (limits) | 1,460 (none) | 1,044 (1,600) | 984 (1,600) |
| application startup, median of restarts | 4.71 s (5) | 5.00 s (5) | 2.85 s (7) |
| application image on disk | 596 MB | 596 MB | 748 MB |
| run | [baseline](../footprint/2026-11-16-baseline.md) | [final-2gb](../footprint/2026-11-16-final-2gb.md) | [final-aot](../footprint/2026-11-16-final-aot.md) |

Every run passed both smoke tests and the ledger checks, and no container was killed for memory. The baseline had no limits, so the application could grow its heap to 75% of the 15 GiB Docker had.

The lean settings ([ADR 0027](../adr/0027-memory-target-2-gb.md)):

- Application: SerialGC, heap at 60% of the container limit, metaspace capped at 192 MB (it uses about 116 MB). SerialGC and G1 peaked at the same 469 MiB in the same load, and SerialGC used 68 CPU seconds against G1's 74 ([SerialGC run](../footprint/2026-11-16-gc-serial.md), [G1 run](../footprint/2026-11-16-gc-g1.md)); with one run each, treat the CPU difference as a hint. Under 1,792 MB the JVM picks SerialGC on its own; the flag writes the choice down.
- Kafka: heap 256 MB instead of 512 MB. With 192 MB the broker failed at startup with `OutOfMemoryError` in the log manager.
- PostgreSQL: `shared_buffers=64MB`, `max_connections=30`. The Hikari pool stays at 10 connections; it was not measured to matter, so it was left alone.

The limits in `compose.yaml` and `deploy/k8s/base` are 768, 576 and 256 MiB, 1,600 MiB in total, which is 448 MiB under the 2 GB target.

Startup is container start to the first ready answer of `/actuator/health/readiness`. On the same image, the AOT cache brought the median of 7 restarts from 4.73 s ([cache switched off](../footprint/2026-11-16-aot-off.md) with `-XX:AOTMode=off`) to 2.85 s, 40% less ([ADR 0028](../adr/0028-jvm-aot-cache-for-startup.md)). The cache file is 118 MB and the image grew by 152 MB on disk. Nothing in the image could be trimmed for free. The JRE is 192 MB, and the 83 MB of jars are all on the class path.

## Throughput on 2 vCPU

[Run 43990396247](../benchmarks/2026-11-16/results.md) on a 4 vCPU GitHub runner: the application pinned to 2 cores (`taskset -c 0,1`, `-XX:ActiveProcessorCount=2`) with `-XX:+UseSerialGC -Xmx460m -XX:MaxMetaspaceSize=192m`, the same heap the 768 MiB limit gives. Conditional-update strategy, 256 users, 5 repetitions, 30 s warm-up and 60 s measured per cell, as in phase 2 ([ADR 0029](../adr/0029-throughput-per-dollar.md)). The ledger checks passed after every cell.

| hot share | created/s, 2 cores and lean JVM | created/s, phase 2 (all 4 cores, 1 GB heap) | change | p99 ms (201) |
|---|---|---|---|---|
| 0% | 1,861 | 2,042 | -9% | 420 |
| 30% | 1,384 | 1,602 | -14% | 475 |
| 90% | 699 | 983 | -29% | 889 |

Without a hot account the application used about 2 cores (0.49 of 4 logical CPUs), so the 2 cores were the limit. At 90% hot it used about 1.2 cores and still lost the most; the smaller heap or the pinning may explain that, but it was not investigated.

## Limits of these estimates

- The 2 vCPU machine is simulated. Only the application was pinned to 2 cores; PostgreSQL and the load generator ran on the other cores of the runner. On a real 2 vCPU machine, PostgreSQL and Kafka would share those 2 vCPU with the application, so throughput there would be lower than in the table.
- All candidate machines are burstable. B2als v2 has a base CPU performance of 30% (Microsoft's page above) and runs above it only while it has CPU credits; t4g and Lightsail also work with CPU credits. The benchmark kept 2 cores busy for minutes, which a burstable machine sustains only while credits last.
- The runner is x86 (AMD EPYC 9V45). t4g is Arm (Graviton), so its throughput can differ.
- The footprint was measured on Docker Desktop on Windows with 16 CPUs, not on the candidate machines. The memory left for the operating system and Docker on a 2 GB machine was not measured, and k3s or another Kubernetes distribution would need more.
- These are list prices on demand. Disk, data transfer and Azure's public IP are not included, and nothing here comes from a bill.
- One strategy was measured; the phase 2 grid stays the comparison between strategies.
